# 配置、会话与执行记录

日常用户在工作区里对话，应用通过已绑定的制作预设提交任务。RunDesk 需要知道实际使用的引擎、配置和容器，也需要在任务结束很久以后解释某个制品的来源。这个设计把两种需求放在同一条执行路径上。

## 实施顺序与验收

1. 保留工作区、会话、实例和应用预设的已有 ID，确定每类数据的所有者和版本依据。已有 Codex 和 Kun 接口继续负责各自的原生配置。
2. 在任务准入时保存宿主能够确认的配置声明及资源绑定，并把版本引用写入这一轮的输入事件。引擎确认原生执行后，再关联其线程或运行编号。
3. 输出文件通过会话、Run、工作区、路径和内容摘要关联到产生它的执行。同名文件再次发生变化时，应能区分两次记录。
4. 将日常入口收敛到工作区和应用。构建中心管理可复用制作环境。旧链接继续解析到原来的配置范围。
5. 使用旧版状态分别验证重启恢复、历史证据缺失、配置变化、应用授权及制品归属。保留第三种引擎的接口边界，跨引擎交接需要独立验收。

## 数据关系

| 数据 | 身份和归属 | 存储与依据 |
| --- | --- | --- |
| 工作区 | 组织会话和工作文件，可由多个执行环境使用 | SQLite 保存登记信息。文件内容位于已登记工作目录。 |
| 执行配置 | 复用现有实例 ID 和引擎类型。Docker 的实际运行范围还包括工作区 | 宿主保存模型选择、权限、环境及提供方绑定；原生 HOME 中的配置按现有引擎规则读写。镜像只是创建环境的输入。 |
| 应用制作预设 | 某个应用允许使用的环境，具有明确的实例及工作区绑定和启停状态 | SQLite 保存授权关系。每项任务使用其获准的绑定。 |
| 配置声明版本 | 记录准入时宿主已知的引擎、环境、权限和资源引用 | 版本按声明内容区分。资源版本可能表示内容版本、绑定版本，或者仍可变化的原生来源。 |
| 显示快照 | 按引擎、实例及工作区识别，供设置界面读取 | 数据目录里的脱敏文件，可从原生配置重新同步。它的时间不能证明某次历史 Run 实际加载了哪些工具。 |
| 会话与参与记录 | RunDesk 会话保存用户可见的工作历史。其执行者关联指向特定实例、引擎及运行范围 | 原生线程属于对应引擎的会话参与记录。恢复前校验范围；不同引擎的原生句柄不能互换。 |
| Task 与 Run | Task 是应用提交及队列身份；Run 是会话的一次执行 | 准入事件记录实际采用的执行配置及版本。以引擎返回的事件确认原生关联，查询时可以固定事件游标。 |
| 轨迹 | 会话事件按宿主事件 ID 排序，具体执行证据关联 Run | SQLite 事件日志是宿主历史依据。耗时、步骤、摘要、JSONL 导出是基于证据的视图。Kun 自有执行记录继续由其运行时保存。 |
| 制品 | 工作区文件可以在不同 Run 中被改写。内容版本通过摘要区分 | 文件库可保存引用、托管副本或显式归档。引用只承诺能核对原件，归档才承诺保留独立字节。 |

## 声明、绑定、生效

新增记录保存在现有 SQLite 对象表和事件表中。相同范围、相同声明共用一份 `configuration-revision`，每轮 `run/input` 用 `configurationRevisionId` 指向它。会话的参与段有独立 ID，切换执行者会产生新的段；回到已使用过的环境时，原生句柄仍按先前所属的实例、工作区、引擎和状态目录核对。内部回归覆盖 A→B→A 的三段关系。

轨迹的“步骤与耗时”中，选定一个轮次、展开“本轮执行记录”，可以查看固定游标下的声明版本和原生运行证据。生成的个人文件可携带 `runId`。任务资源接口的 `artifacts` 在存在可靠记录且调用者具备文件权限时列出变化的输出文件及其摘要。相同路径后来产生的新内容不能冒充旧版本。

以视频制作中的 TTS 为例，应用批准某个制作环境，那个环境的 MCP 配置提供具体的服务连接。RunDesk 可以记录工具来源、作用范围以及平台策略。工具是否实际启动、调用成功，需要相应引擎的运行记录。服务的凭据随授权传递，历史配置记录只保存可公开的元数据。默认本机 Codex 继续使用服务账户的原生 HOME，Docker 使用对应环境的持久 HOME。

应用设置修改可用预设，构建中心准备镜像和环境。环境设置对话框显示正在修改的工作区。旧任务的执行版本不会随着今天的模型、MCP 或 Skills 设置发生变化。外部编辑的原生文件照常由引擎读取；读取界面快照不会改写这些文件。

## 跨引擎接力的验收边界

目前日常执行使用 Codex，Kun 用于内部维护。接入另一种日常引擎时，应验证以下过程。

1. 第一位执行者完成这一轮，制品与未完成事项关联到这次 Run。
2. 接手请求固定公共对话游标、获准的制品版本和目标执行配置。在新一轮准入时重新核对应用权限和环境能力。已排队的任务、待审批操作与终止命令继续指向原执行者。
3. 新引擎建立自己的原生线程，并记录实际接收的交接信息。如果第一位执行者随后回来，要确认它还需要哪些公共消息。线程不能恢复时，可以从已确认的交接点建立新的执行关联。

支持这项工作还需要真实的第二个日常引擎、上下文传递以及故障恢复验证。本版没有向用户提供 Claude Code、Pi 或自动跨引擎接力入口。

新适配器的接入点包括 `RuntimeBackend` 的准入、执行与停止，平台资源声明到引擎原生配置的映射，以及原生回执到宿主事件的关联。通过工作区隔离、工具授权、线程恢复和制品来源测试后，再把该引擎加入日常会话的可选范围。

## 兼容与备份

实例记录在下一次正常保存时使用带 `schemaVersion` 的存储格式。引擎类型由宿主管理，引擎选项由对应适配器解释；已有 `agentRuntime` 和 `codexHome` 字段保持兼容。读取旧记录无需批量改写。未知引擎的原生选项可以保留，未注册对应适配器时不能启动或使用 Codex 替代它。高于支持范围的存储版本会明确报错，避免覆盖较新记录。

保留原来的数据目录、原生 HOME、工作区和镜像。历史查询以当时保存的事件为准；旧记录缺少引擎确认、配置版本或制品来源时保持未知。备份应在一致的时点纳入 SQLite、受管原生状态及已归档制品，并单独备份引用的外部工作目录。显示快照和导出文件可以重建。

原生状态目录也是续接校验的一部分。异机恢复时应核对原来的绝对路径及 Docker 挂载，避免把旧线程交给另一个状态目录。
