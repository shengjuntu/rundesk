# HTTP 500 与运行错误排查

日期：2026-10-03。基线：RunDesk 0.8.2；修复版：0.8.3。

## 结论与范围

扫描了后端所有显式 500 返回、API 错误封装、RPC 进程/协议、任务启动、存储和技能替换路径，并对可重现的传输问题做了故障测试。没有用户当次请求的 response、requestId 或服务器日志，因此不能把以下发现认定为那次 500 的根因。

0.8.2 并非把所有异常统一返回 500：普通 `respond` 默认 400，任务提交/审批默认 409，v1 的类型化错误再覆盖状态。WebUI 使用 v1。任务提交的 202 只表示接收；后续模型服务的 HTTP 500 通常通过 Codex 事件或会话 error 出现，不是该提交接口返回的 500。

## 本地 500 来源清单

| 位置 | 触发条件 | 0.8.3 处理 |
| --- | --- | --- |
| `internal/app/api_v1.go` · `GET /requests/{key}` | 数据库关闭、读取故障，或记录不能解码 | 503 `storage_unavailable`；保留底层错误链与 requestId。数据库故障本身仍需修复 |
| `internal/app/skill_bundles.go` · `ImportSkillBundle` | 新目录安装失败，旧目录自动恢复也失败 | 保留 500 `skill_restore_required` 和备份路径；新增安装与恢复两次失败原因。不能假称安装成功 |
| `internal/app/http.go` · `events` | ResponseWriter 不支持流式刷新 | 保留内部错误。标准服务与当前中间件支持 Flusher，正常入口不应走此分支；不是网络断连的通常来源 |
| `internal/app/http_diagnostics.go` · `diagnosticBoundary` | HTTP handler panic，且尚未写出响应 | 保留 500 `internal_panic`，堆栈仅写服务日志。已开始的 SSE/文件流中断，不拼接 JSON |
| `internal/app/api_v1.go` · 幂等回放，经过上述 panic 兜底 | 数据库里的 completed 回执状态码缺失/无效，旧代码把 0 传入 WriteHeader | 新增状态码/JSON 校验，503 `receipt_invalid`；不会重新执行原操作 |

补充：标准库的静态文件服务和 `http.ServeContent` 在文件读取/定位失败时也可能产生 500；反向代理、Codex、模型服务可以独立产生自己的 500。这些不等同于上表的显式业务分支。随机 ID 生成中的极端随机源故障也存在终止分支，不能靠把错误状态改为 200 来解决。

## 已确认并修复的执行问题

| 问题 | 修复前故障复现/证据 | 修复与验证 |
| --- | --- | --- |
| 调用期限不约束 stdin 写入 | 子进程不读 stdin；2 MiB 请求在 100 ms 期限后仍卡住，2 秒观察窗失败 | 期限覆盖排队/写入/等回复；部分帧写入超时会关闭该连接，不重发；测试通过 |
| 已取消的调用仍会发送 | 先取消 context，再调用，out 轨迹仍记录 1 次发送 | 发送前检查取消；测试确认 0 次发送 |
| 损坏 JSON 被忽略 | 子进程输出非 JSON 后不退出，原调用一直等到超时 | 立即记录协议原因并清理进程，不再无意义等待；测试通过 |
| stderr 长行堵塞 | 2 MiB 日志超过原 Scanner 1 MiB 上限；停止读取后，子进程无法完成日志输出和正常回复 | 持续排空；每行最多展示 64 KiB 并标记截断；正常回复仍可收到 |
| 进程退出原因丢失 | 模拟 exit 7，原调用只得到泛化的 exited | 保留实际 exit status/读取原因，供 HTTP 详情和运行错误使用 |
| 失败连接留在缓存 | 初始化失败分支只 Close，没有清除 handle；配置调用错误也未主动移除坏连接 | 初始化失败、配置传输损坏/超时后清理；下一次显式操作建新连接；测试检查缓存与恢复 |
| turn/start 确认缺失仍标 running | 原代码忽略 JSON 解析错误且不检查 turn.id | 标记失败与提交不确定，保留线程供核对；测试确认只发出一次 turn/start |
| 事件记录失效后仍可接受新任务 | 原 Start 未检查 manager 取消；输入事件写失败被吞掉后仍启动执行 goroutine | 拒绝失效后台的新任务；输入落盘失败返回 503，尚未调用 Codex；通过数据库 trigger 注入写失败验证 |
| 不完整回执触发内部异常 | 原回放未检查 HTTPStatus，可能调用 WriteHeader(0) | 返回明确错误并保护原回执；验证不 panic、不增加第二个工作区 |

这些是实际控制流、资源清理与协议确认修复，不只是替换 HTTP 数字。没有加入自动重跑任务或自动重复写配置。

## API 分类

v1 中，原生 RPC 错误一般映射 502；原生参数拒绝为 400；缺少方法为 502 `codex_method_unsupported`；进程不可用和连接数已满为 503；调用超时为 504。保留原始 RPC code/data、错误链与诊断关联编号。500 留给真实内部问题与无法恢复的技能安装。

旧 `/api` 业务接口的默认状态保持兼容，新增代码和详情可用于定位。请求记录读取异常现为 503。已经保存的幂等回执仍按原状态回放；仅对不合法回执阻止回放。失败的写操作可能已经产生副作用，不能凭 502/503/504 就换 Key 重发。

## 尚不能保证的部分

- 无法保证外部模型服务、网络或代理不再返回 500，也没有把这些错误转换为成功。真实 provider 的稳定性必须在部署环境确认。
- 这次没有覆盖所有磁盘满、文件权限变化、数据库损坏或内核级 I/O 卡死组合；明确的故障仍会返回错误。数据库现有 WAL、busy_timeout 和单连接配置保留，没有引入盲目写重试。
- HTTP panic 兜底不等于全部后台 goroutine 的恢复机制；不吞掉任意程序错误继续运行。
- 测试使用独立的 JSONL 故障子进程和演示协议，不是用户的真实 Codex/provider；Windows 仅交叉编译。

## 再次遇到错误时

在「错误记录」复制失败接口、时间、requestId 和响应详情。若来源是 Codex 运行，保留 session/turn/event 编号与原始错误。用 requestId 对照服务日志中的 `api_error` 或 `api_panic`；HTML 错误页则同时核对代理日志。这样可以确定是哪一层失败，再处理对应原因。
