# 个人文件与产物资源

## 存储约定

本次在 v0.52.0 基础上将个人文件分为三种明确的存储方式。文件目录仍是个人的；所有权取自认证身份，不能由请求参数指定。

| storage | 内容归属 | 适用入口 | 原文件修改或移除后的行为 |
| --- | --- | --- | --- |
| `reference` | 原工作区拥有内容，个人库保存引用、大小和 SHA-256 | 会话上传、每轮新增或修改的正式产物 | 版本不匹配返回 409；来源丢失返回 410，不把新内容冒充旧产物 |
| `managed` | 个人库拥有原始内容 | 直接上传到个人库、v0.52.0 已有文件 | 独立于工作区保留 |
| `snapshot` | 个人库拥有显式归档的内容 | 对当前有效引用执行「归档」 | 保留该版本，独立于后续工作区修改或清理 |

工作区上传只落一份内容。自动收录只新增 SQLite 元数据，不再默认向 `<data>/personal-files/<owner>/<fileId>` 复制。引用保存 `source.workspaceId` 和工作区相对路径，不把宿主绝对路径当作资源身份。目录可迁移，但文件版本仍由大小和 SHA-256 校验。

直接上传到个人库没有另一份工作区原件，因此个人库就是它的原始存储。显式归档把现有引用提升为 `snapshot`，保留相同 ID、所有权和内容身份，不新增重复目录项。归档重复调用保持相同结果；在原文件已经改写或删除后，不能凭引用恢复旧内容。

## 使用与执行环境

- 「我的文件」支持搜索、预览、下载、删除；引用文件可显式归档。
- 会话「＋ → 上传文件」上传到工作区，同时登记个人引用。
- 「＋ → 从文件库加入」复用已有个人目录项。同一工作区的上传引用可直接复用；跨工作区或从独立库内容加入时，显式物化成目标 `uploads/` 附件，以满足本机／Docker 的输入路径和权限约束。此处是向执行环境交付内容，不是额外保留一份个人归档。
- 会话结束时，登记本轮新增或修改的 `outputs/<sessionId>` 文件。工具缓存、源码依赖和工作区其他文件不自动当作正式产物。
- 需要保证旧版本在下一轮覆盖后仍能读取时，应先显式归档。引用模式没有历史内容副本。

引用下载会先将本次实际读取的字节写入临时缓冲文件并校验哈希，再发送响应，结束后删除缓冲。这样即使 Agent 在响应期间继续改写原文件，也不会把混合内容当作已记录版本发送。缓冲不是持久归档；下载不会把存储方式自动改成 `snapshot`。附件物化和归档也校验实际复制的字节，校验失败不登记结果。来源路径拒绝路径越界和符号链接别名。

## 归属与删除

管理员、普通用户各有自己的个人库；同一应用项目的成员不能读取对方的目录。将个人文件加入会话，仍会把内容提供给该会话及其执行环境，会话自身原有的应用／项目权限不变。

生成文件归本轮任务发起人。共享会话后续用户只登记自己轮次新增或修改的产物；个人身份提交的队列任务和恢复轮次保留归属。纯应用 API 凭据没有个人身份，不能访问个人库，也不会把后台任务文件放入某人的个人库。

删除 `reference` 只移除个人目录项，不删除或撤销原工作区文件。原文件继续按工作区自身的权限提供访问。删除 `managed` 或 `snapshot` 会移除个人库拥有的内容。所有类型都保留目录墓碑，本人再次通过该个人文件 ID 下载或附加时返回 410。

此前已向其他工作区物化的附件，以及 v0.52.0 的历史附件，保留原有的删除墓碑语义：RunDesk 阻止通过这些关联附件再次下载或提交。删除不是对已执行任务的撤销，也不会清理模型自行复制的内容或备份。删除会话只删除平台会话记录，不清理工作区原件；引用能否继续读取取决于原件是否仍存在。

## 限额与升级

上传保持 32 MiB 限制；单个自动登记的生成文件最多 512 MiB；个人目录最多 10000 个有效文件、逻辑大小合计 10 GiB。引用也计入逻辑限额，避免无限登记；归档保留原目录项，不重复计数。容量或读写错误返回结构化错误，自动收录失败记录为 `library/error` 执行事件。

v0.52.0 已有记录没有 `storage` 字段，读取时视为 `managed`，已有内容原地保留，不自动删除、迁移或转换成引用。更早且没有可靠个人所有权的工作区文件不自动猜测归属。

## API

使用个人 Cookie、个人访问码或管理员认证；应用凭据无权调用。

- `GET /api/v1/library?q=文件名`：本人目录，返回 `storage`、可选 `source` 和 `snapshotAt`。
- `POST /api/v1/library`：multipart 字段 `file`，直接保存个人库拥有的原始内容。
- `GET /api/v1/library/{fid}/content`：下载；`preview=1` 请求安全预览；响应 ETag 基于 SHA-256。
- `POST /api/v1/library/{fid}/snapshot`：JSON `{}`，传 `Idempotency-Key`，将本人当前有效引用显式归档。同一 ID 已经拥有独立内容时直接返回。
- `DELETE /api/v1/library/{fid}`：删除本人目录项；是否移除内容由上述存储归属决定。
- `GET /api/v1/library/deleted-references`：本人已删除的物化附件墓碑；原始工作区引用不在此列表中。
- 原有 `POST /workspaces/{wid}/uploads` 除 `file` 外，可用 multipart 字段 `libraryFileId` 加入本人的文件；响应 `materialized` 表示是否向执行环境创建了附件内容。成员仍通过 `/member/{grantId}/workspaces/{wid}/uploads`，项目写入权限照常检查。

`personal_file_source_changed`（409）表示来源已不是收录版本；`personal_file_source_missing`（410）表示来源丢失；`personal_file_source_invalid`（409）表示不安全或无效来源。调用方应展示失效引用或要求选择当前文件，不能自动改写目录里的内容身份。
