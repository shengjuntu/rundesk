# 用户与项目授权（0.11.0）

RunDesk 有两类入口：管理员使用通用助手和管理界面；普通用户登录后进入应用项目。应用 API 凭据继续用于 news2douyin、video-app 等程序，不等同于人的账号。

## 启用

1. 备份现有数据目录，并配置 `RUNDESK_TOKEN` 作为管理员凭据。已有用户时移除该配置会拒绝访问，避免退回无认证模式。
2. 管理员在应用页绑定 Docker 专用配置，在运行环境页为应用创建项目环境。
3. 打开「用户与授权」，创建用户，勾选应用项目，选择「只读」或「可执行」。
4. 保存一次性展示的个人访问码，经可信渠道交给用户。用户在原登录页填写个人访问码，自动进入成员入口。

个人访问码是系统生成的高熵凭据，不是用户自设密码；没有邮件找回、SSO 或多因素认证。丢失时由管理员重置。数据库只保存哈希。部署到远程网络时通过 HTTPS 提供服务，配置正确的 PublicOrigin。

## 权限

| 操作 | 管理员 | 可执行成员 | 只读成员 |
|---|---|---|---|
| 通用助手、用户、Skills/MCP、镜像和 Docker 管理 | 可以 | 不可以 | 不可以 |
| 查看被授权应用项目的任务、执行过程和文件 | 可以 | 可以 | 可以 |
| 创建与继续任务、上传、停止、审批 | 可以 | 可以 | 不可以 |
| 删除共享历史、修改运行配置、队列与 Cron 管理 | 可以 | 不可以 | 不可以 |

授权单位是「应用 + 项目」，同一项目是协作边界：所有被授权成员都能看到该应用在项目中的任务和文件，可执行成员能够继续或停止共享任务。需要私有数据时使用不同项目并分别授权；容器不按用户或会话自动创建。普通用户不能使用本机 Codex；应用改为本机执行后成员写操作被拒绝。

这里实现的是服务端资源访问控制，不是敌对租户安全沙箱。Docker daemon、宿主机管理员及应用内工具本身仍属于可信部署边界；不要把宿主机敏感目录或 Docker socket 挂入成员应用。

## 登录和撤销

成员浏览器使用独立的 HttpOnly、SameSite=Strict Cookie，12 小时到期，不把个人访问码放进浏览器存储。每用户最多 20 个有效浏览器登录。退出会删除当前登录记录。

停用账号、修改授权或重置访问码会使现有浏览器登录失效，并终止后续事件流访问。重置后旧访问码失效。修改授权后原访问码仍可重新登录，以获取新权限。停用不会自动取消已经接收的运行任务；需要管理员另外停止任务。账号保留用于记录，不提供删除接口。

## API

- 管理员：`GET/POST /api/v1/users`、`PUT /api/v1/users/{uid}`、`POST /api/v1/users/{uid}/access-code`。
- 创建参数：`name`、`grants`；新账号始终启用。更新参数还包含 `enabled`、当前 `revision`。重置提交当前 `revision`。
- 成员：`GET /api/v1/member/catalog` 返回当前用户和授权项目；使用返回的 `grant.id` 请求 `/api/v1/member/{grantId}/sessions` 等受限资源。可以用个人访问码作为 Bearer，也可以用登录 Cookie。
- 成员不能直接调用管理员路径或应用根路径。服务端校验 grant、应用、项目及会话来源，不依赖界面隐藏。
- 创建会话与提交轮次需要 `Idempotency-Key`；不同用户、授权修订具有独立回执空间。网络错误后先核对结果，不能随意更换 Key 重跑。
- 完整参数与成员路由投影见 `internal/app/openapi.json`，API 文档版本 1.10.0。

## 升级

停止旧程序并备份数据目录，替换二进制后使用原参数启动。原管理员、应用凭据和现有任务继续保留；新用户记录按需创建。降级前应停用新增成员并保留升级前备份，旧版本不理解这些授权记录。
