# 独立诊断会话（RunDesk 0.30.0 / Kun 0.7.0）

在会话顶部打开“调试检查”，选择一个轮次，展开“用独立会话诊断”，输入问题并点击“创建诊断并发送问题”。Kun DevTools 的 Console 也提供“独立诊断”入口。创建和发送需要显式操作，普通查询、查看证据或刷新不会调用模型。

新的诊断会话沿用来源的实例、模型和认证，分别记录问题、模型请求、工具结果和用量。来源可以继续运行或保持暂停；诊断不会给来源追加解释问题，也不停止、继续、审批或重跑来源。诊断过程会把读到的证据发送给该模型服务，是否联网取决于已配置 endpoint。费用未估算，缺失 usage 不视为零。

## 固定来源与工具

`POST /api/v1/sessions` 的 `traceAnalysis` 接受 sessionId、runId、可选 eventIds 和可选 through。管理员入口沿用原有幂等机制；应用 key 与成员入口没有因此获得创建分析会话的权限。

```json
{"traceAnalysis":{"sessionId":"SOURCE_SESSION","runId":"SOURCE_RUN","through":123}}
```

through 为宿主事件 ID。省略时取创建时最新；提供时保持该上界，包括显式 0，空历史不允许创建诊断。未知轮次、越界事件和未来上界拒绝。返回 Session.traceOrigin 保存最终上界；之后向新会话的 `/turns` 发送问题。追问保持原范围，要分析新记录须新建诊断。

Kun 在首次诊断运行前导出独立 SQLite 来源快照，只复制该来源会话与上界内事件；执行库、模型用量和诊断消息写到新会话。导出前限制 100000 条事件、128 MiB 总载荷、单条 8 MiB；查询仍受 0.28.0 的生命周期重建上限约束。快照可含本会话其他轮次，选定 run 为诊断重点；明确比较其他轮次时可查询同一固定来源中的其他轮次，不能跨来源会话。

诊断复用 Kun 原有模型/工具循环、预算、取消与事件持久化，具有专用工具目录：

| 工具 | 用途 |
| --- | --- |
| trace_list_runs | 固定来源的轮次分页 |
| trace_find_steps / trace_find_issues | 步骤、异常信号与预览筛选 |
| trace_get_step | 步骤及证据引用 |
| trace_read_event | 已脱敏事件的 Unicode 分块 |
| trace_statistics | 已记录步骤与耗时统计 |
| trace_propose | 生成待审核建议，无应用动作 |

不继承业务 MCP、文件工具、Skills、项目笔记和业务系统提示词。模型即使请求 write_file、其他工具或任意 SQL，也不能通过目录及参数校验。没有 shell、任意文件路径、跨来源选择或执行控制工具。沿用模型与执行预算，来源任务的断点默认值不复制给诊断。输入仅允许问题文本，附件和技能会被拒绝；继续追问可保留诊断历史，不提供诊断检查点续跑。

模型指令要求区分记录事实、带不确定性的推断、缺失证据和建议，并将来源文本作为不可信证据；这不是对模型回答正确性或遵从性的保证。结构化密钥先脱敏再进入查询；自然语言和字符串内部可能仍含用户内容，沿用会话权限和既有脱敏边界。

## 建议的含义

`trace_propose` 接受 runId 和 proposal。proposal 包含 kind（inspect / steer / configuration）、reason、text 和 1–16 个不重复的 evidenceIds。引用必须属于该运行在固定快照中可归属的生命周期事件；截断引用或无法归属的记录可能不被接受。不存在、其他轮次/会话或越界引用被拒绝。

返回 suggestion_only、内容指纹 ID、来源会话/轮次/through、建议文本及引用。Kun 限定建议目标为选定诊断轮次，记录在诊断自己的工具完成事件中，并在会话显示卡片；点击引用打开原始事件，保留相同 through。模型没有调用建议工具时，只显示普通分析文字，不伪造结构化卡片。

引用存在且归属正确不证明模型解释正确。建议本身不是控制回执，不代表修改已提交。诊断模型没有 apply 工具；0.30.0 增加独立的管理员审核入口，仅接通 steer（补充指令）建议。inspect 和 configuration 仍由人工处理。

## 审核、预览与发送（0.30.0）

1. 在补充指令建议卡片点击“审核与执行记录”，阅读原建议和引用，编辑“审核后的补充指令”。
2. 点击“预览当前控制目标”。宿主重新读取成功的 `trace_propose` 工具事件并校验固定证据，读取来源的当前状态；只允许原轮次仍活动的 Kun 运行。保存精确文本、runId、revision 和一个控制 requestId，来源状态和事件不变。
3. 核对预览后点击“确认发送到来源运行”。请求只能引用已保存的预览，不能传入另一个目标或操作。worker 在执行时再次校验运行编号和状态版本；过期后需要重新预览。修改文本也会使页面当前预览失效。
4. 查看记录。排队不会解除暂停，也不会审批 MCP。只有后续 `kun/control.applied` 才表示文本已写入运行上下文；终止前未应用的指令可得到 rejected。已生效不等于业务任务成功。

历史建议不能重定向到来源的新轮次。检查/配置建议、Codex 原生建议不通过本入口执行。新的审核接口仅管理员可用，应用凭据和成员入口默认拒绝；没有向诊断模型增加工具。

| 接口 | 行为 |
| --- | --- |
| `POST /api/v1/sessions/{diagnosticId}/diagnostic/reviews` | 输入 `proposalEventId`（诊断会话的宿主工具完成事件 ID）和 `text`（1–4000 字符）；创建不可变预览 |
| `POST /api/v1/sessions/{diagnosticId}/diagnostic/reviews/{reviewId}/apply` | 输入 `{}`；明确发送保存的命令，同一 reviewId 重试复用同一 requestId |
| `GET /api/v1/sessions/{diagnosticId}/diagnostic/reviews?proposalEventId=...` | 返回该建议最新 20 个预览及其回执，结合来源保留事件显示最新已知结果，不启动 worker |

预览记录包括建议原文、审核文本、固定证据来源、观察到的状态/阶段、目标版本、提交时间与回执。`receiptEventId` 可打开来源的原始控制事件，独立于建议的旧证据范围。刷新网页和宿主重启后记录保留；没有回执时不推断成功。

发送前先保存命令。发生超时或响应丢失时，记录可能显示 unknown；应刷新记录或重试同一个 reviewId，不能把未知结果当作失败并新建预览重复发送。重试由 worker 持久化命令账本去重，已保留的回执可离线读取。若 worker 已回收且回执尚未导入，接口报告离线，不为核对或发送而自动拉起、恢复运行。不同预览是不同明确操作，不宣称建议内容级别的全局去重。

审核记录的最新状态以保留的宿主回执为依据，可能有事件导入延迟；未提供实时推送、任意历史分叉、自动配置修改或独立业务成功验证。

## Codex 与边界

Codex 保留原有独立原生分析线程，挂载同一 trace MCP；0.29.0 已补固定上界参数、严格工具参数和 trace_propose。其原生只读沙箱与继承工具配置仍按原路径处理，不宣称与 Kun 专用工具目录有完全相同的隔离保证；Kun 建议卡片是已验证的结构化展示路径，Codex 可通过原生工具结果查看建议。

没有诊断器跨实例选择、LLM 生成补丁的自动应用、历史分叉、外部工具结果重放或业务成功验证器。Kun 新诊断只读宿主保留日志，不连接来源 worker 的实时内部状态；需要后续记录须新建范围。

本版 Kun 仍为 0.7.0、worker 协议仍为 v7。0.29.0 用户升级 RunDesk 即可，建议使用同包源码构建以保持一致；从 0.28.0 或更早升级时须同步替换两个命令并结束旧 worker。旧快照继续可读，旧引擎检查点不跨引擎版本恢复。本地模型夹具和浏览器测试见 [KUN-VALIDATION.md](KUN-VALIDATION.md)，真实模型/Codex/MCP 业务闭环仍待验收。
